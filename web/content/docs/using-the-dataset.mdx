If you'd rather not call the API, the compiled dataset is committed as plain
YAML you can read directly from the repository.

## Where it lives

```
data/
  series/        one file per Series or Franchise, keyed by id
    demon-slayer.yaml
    fate.yaml
  staff/         voice actors, grouped by language
    japanese-voice-actors.yaml
```

Every file under `data/` is **generated** by `builder build` and carries a
`# Generated by builder build — do not edit` header. Treat it as read-only
output; the authored inputs live under `builder/config/overrides/` (see
[Building the dataset](/docs/building-the-dataset)).

## The data model

The catalog is a hierarchy:

- **Franchise** — a brand grouping related Series (e.g. *Fate*). Carries
  `series` and optional curated `watchOrders`.
- **Series** — one continuity / storyline, the base unit. Carries `seasons`,
  `movies` and `specials`, plus an `ordering` (see below).
- **Season** — one numbered TV installment (one broadcast run, i.e. a *cour*),
  with `number`, release info, `externalIds` and `episodes`.
- **Movie** / **Special** — films and side content (OVA / ONA / special).
- **Episodes** — a season's or special's episode numbering, stored as the facts
  it is computed from rather than as a list. See [Episode numbering](#episode-numbering).

A file's top-level key — `series:` or `franchise:` — determines its kind, not
its directory. Standalone series and multi-storyline franchises both live under
`data/series/`.

## Example

```yaml
# data/series/demon-slayer.yaml
series:
  id: demon-slayer
  titles:
    original: 鬼滅の刃
    translations:
      en: Demon Slayer
  ordering: absolute
  seasons:
    - id: demon-slayer-s1
      number: 1
      releaseYear: 2019
      releaseSeason: SPRING
      externalIds:
        anilistId: 101922
        anidbId: 14107
        tvdbId: 348545
      episodes:
        count: 26
        absoluteFrom: 1
```

## Episode numbering

A season or special stores `episodes` as a small block, not a list:

```yaml
episodes:
  count: 26          # how many episodes the installment has
  absoluteFrom: 27   # optional — the absoluteNumber of its first episode
  airedFrom: 13      # optional — its first airedNumber; absent means 1
```

Expand it and you get the episodes: `airedNumber` runs from `airedFrom` (or 1)
for `count` entries, and `absoluteNumber` runs from `absoluteFrom` alongside it.
The API does exactly this and serves one `Episode` per episode, so nothing about
the wire format changed — this is how the dataset is *stored*.

It is stored this way because every one of those numbers is derived. The only
episode-level fact any source publishes is a count:
[anime-offline-database](https://github.com/manami-project/anime-offline-database)
has one `episodes` integer per entry and nothing else — no titles, no air dates,
no per-episode records at all. Writing the expansion into `data/` cost 6,422
lines, a third of the committed dataset, to say what three fields say.

**`ordering` on the series tells you which sequence to trust:**

- `absolute` — one linear storyline, so its installments carry `absoluteFrom`
  and that continuous count is the order (*Demon Slayer*, *Fate/Zero*).
- `release` — no single linear stream, so there is no `absoluteFrom` anywhere in
  it and the installments sort by release date. *Fate/stay night* is the case:
  the 2006 series, *Unlimited Blade Works* and *Heaven's Feel* retell the same
  Holy Grail War from different routes, so numbering them continuously would
  assert an order that is not real.

`ordering` is derived by the build from the same decision that assigns the
numbering, so the two cannot disagree. Note it is scoped to a **Series**, not a
franchise: *Fate* holds `fate-zero` and `fate-strange-fake` as `absolute` — each
counting from 1 independently — alongside `fate-stay-night` as `release`. For
ordering *across* series, see a franchise's `watchOrders`.

## Titles

Each node stores a `titles` block: the native-script `original` plus
`translations` keyed by [BCP-47](https://www.rfc-editor.org/info/bcp47) code
(`en`, `ja`, `ja-Latn`, …). The API resolves these to a single string per
request; when reading the YAML directly you get every language.

`en` means an English **title** and `ja-Latn` means the Japanese one
*romanized*. They are different facts and are kept apart: `jujutsu-kaisen` is
`呪術廻戦` with `ja-Latn: Jujutsu Kaisen` and no `en` at all — nobody translated
that title, they transliterated it — while `demon-slayer` is `鬼滅の刃` with both
`ja-Latn: Kimetsu no Yaiba` and `en: Demon Slayer`. 61 of the 152 series carry
an English title.

The open anime catalogues do not record that fact. anime-offline-database has
one title field, which holds the romanization, and a `synonyms` bag with no
language tags at all — for `葬送のフリーレン` it carries four English strings, of
which one is the licensed title and three are literal glosses, and nothing
distinguishes them. So a title auto-filled from *it* is `original` + `ja` +
`ja-Latn`, never `en`.

The English title comes from Wikidata instead. A **series** is the one node with
no id to join on — it spans several AniList entries, one per installment — so
`builder init` finds its work by looking the native `original` up as a Japanese
Wikipedia article, keeping the match only when the entity says it is a kind of
work. The builder then fills `en` from that entity's `P1476` title claim, or its
English label where it has no claim, and records the work as
`externalIds.wikidataId`. This is why `sousou-no-frieren` carries
`en: Frieren: Beyond Journey's End` rather than its romanization.

Nothing about that is authored. 61 of the 152 series get an English title from
`builder init && builder build` and no other step; an `externalIds.wikidataId`
written into an override exists only to correct a resolution that is wrong, and
overrides it when present.

Two rules bound that fill. A candidate that turns out to be the title we already
hold, respelled, is refused rather than stored: `Hyakki Yakōshō` is the `ja-Latn`
`Hyakki Yakou Shou` with macrons, and `Golden Kamuy` is a Latin-script original
the label merely repeats. And an authored `en` always wins. A series naming no
work simply has none, and the API falls back to the romanization. Seasons,
movies and specials are not filled this way: they have no Wikidata id, only an
AniList one.

`builder init` prints what did not resolve and why — a title matching no
article and a title matching a disambiguation page are different problems with
different fixes, and neither is visible from the dataset afterwards.

Two edges are worth knowing. A title written in Latin script with no
native-script form is neither an English title nor a romanization — it is the
`original`, since *Fate/stay night* is written that way in Japan too. And a
title whose original is not Japanese carries its own romanization tag, such as
`ko-Latn` for `메탈카드봇W`.

## External IDs

Every node cross-maps to external databases via `externalIds`: `anilistId`,
`anidbId`, `tvdbId` and `wikidataId` (all optional; `tmdbId` is in the schema
but nothing fills it). Use these to fetch
*expression* — artwork, synopses, ratings — live from those services at runtime.
The dataset itself stores only **facts** (ids, titles, structure), never
licensed descriptive content.
